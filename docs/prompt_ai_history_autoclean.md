# 任务：为 Antigravity 搭建「14 天历史对话自动清理」任务

## 0. 协作方式（请先遵守，再动手）

1. **动手前先复述**你对需求的理解（要删什么、什么条件下删、怎么触发），等我确认后再执行。
2. **删除类操作必须先出清单**：先用只读模式列出将要删除的全部条目（数量、体积、时间范围、代表性文件名），我确认后才允许实删。
3. **在我确认之前，不得删除任何东西**。脚本默认必须是「只报告不删除」模式。
4. 输出用中文，Markdown 结构化（标题、列表、表格、加粗），便于我直接复制到文档里。
5. 遇到第 8 节列出的任一情况，停下来问我，不要自行决策。

## 1. 目标

在 Windows 上搭建一个自动清理任务，删除 **Antigravity** 中超过 **14 天** 的历史对话与缓存数据，同时保证不会损坏正在使用中的数据。

## 2. 硬性约束（不可违反，违反即视为任务失败）

1. **白名单删除**：只允许删除明确列出并经我确认的目录与文件类型。程序本体、记忆/身份文件、技能（`skills/`）、插件、连接器、配置、凭据、备份，**永远不碰**。
2. **绝不强制杀进程**：禁止 `taskkill /F`、`Stop-Process -Force`。强制终止才是数据库损坏的真正原因，只允许发送关闭主窗口的优雅请求。
3. **进程退出后才写数据库**：只有在 Antigravity 进程不再持有数据库时，才允许改索引或删文件。
4. **先备份，再删除**：删除前完整备份 `state.vscdb`（含 `-wal` / `-shm` 旁路文件），保留最近 5 份，滚动覆盖。
5. **默认只读**：脚本默认「只报告」，必须显式传参才进入实删模式。
6. **触发时机用「Windows 登录后 2 小时」，不要用每日固定时间点**。理由：定在每天上午 10 点，万一那天没开机就漏跑。

## 3. 第一步：先核实数据布局，不要照搬任何假设

Antigravity 可能有**两套并存的配置目录**（经典版与 2.0 独立版），动手前必须先确认哪一套是活跃目录：

- `%APPDATA%\Antigravity\`
- `%APPDATA%\Antigravity IDE\`

判断方法：看两个目录 `User\globalStorage\state.vscdb` 的最近修改时间，以**较新**的为活跃目录；两者时间接近就停下来问我。

然后给我一张表：

| 存放位置 | 内容是什么 | 是否属于"历史对话" | 当前超期数量与体积 |
|---|---|---|---|

需要区分清楚的两处（**都必须清理，只清一处等于没清**）：

- **对话正文**：`.pb` 文件
- **侧边栏索引**：`state.vscdb` 里的索引键

请给出**证据**证明两者对应同一批对话（例如 `.pb` 文件名与索引里解出的会话 UUID 做匹配，报告匹配率）。匹配率不是 100% 就要停下来问我。

## 4. 安全门（这是整个任务的核心，必须实现）

执行顺序严格如下：

1. **先算计划**：如果没有任何超期项，**直接退出**，全程不打扰 Antigravity、不做任何检测。
2. **判断进程状态**：
   - Antigravity **未运行** → 立即判定安全，直接执行清理。不需要等空闲、不需要关闭什么、**不要**自作主张启动它。
   - Antigravity **正在运行** → 必须同时满足以下全部条件才继续：
     - 键鼠空闲 ≥ 10 分钟（用 `GetLastInputInfo` 这类系统接口）
     - 没有正在执行的任务
     - 近期没有会话活动
   - 条件满足 → 发送优雅关闭请求 → 等待进程退出（超时 90 秒）→ 继续
   - 条件不满足 → 每 30 分钟重试一次，最多 6 次；都没等到就放弃本次，什么都不删
3. **备份 `state.vscdb`**。
4. **按附录 A 推荐的顺序处理索引与正文文件**。
5. **清理缓存目录**（`Cache/`、`GPUCache/`、`CachedData/`、`Code Cache/` 之类），只删超过 14 天的文件。
6. **重启 Antigravity**——**仅当本次是你自己关闭的**才重启。索引重建发生在下次启动时，无需额外操作。

## 5. 四个已经踩过的坑（务必规避）

**坑 A：Electron 类应用有十几个进程，别要求"全部退出"才算成功。**
主进程 + 渲染进程 + GPU + 工具进程 + 崩溃上报进程，后者退出后常滞留。判定改为：全部退出，或「带主窗口的进程已清零 且 剩余进程数不超过初始值的 25%」。
可以放宽的原因：**真正兜底的是 SQLite**——若仍有进程占用数据库，写操作会拿到"数据库被锁定"而失败，此时中止即可，不会造成损坏。

**坑 B：绝不能只删正文、不处理索引，也不能反过来。**
只删 `.pb` 会留下"列表里有、点开是空的"孤儿条目——比留下几个孤儿文件糟糕得多。
**也不要尝试把 protobuf 索引解码再重新编码写回**（见附录 A），那是最容易损坏数据的做法。请严格采用附录 A 的"删索引键 + 让程序自动重建"方案。

**坑 C：顺序上要先动索引、后删文件。**
先删除索引键，再删 `.pb` 文件。这样任何一步中断的最坏结果都是"什么都没删掉"，而不是"删了一半"。反过来做，一旦中断就产生孤儿条目。

**坑 D：中文 Windows 上的编码问题。**
- 脚本读写文本必须显式指定 `encoding="utf-8"`，不要依赖系统默认代码页（中文 Windows 默认 GBK/CP936）。
- 日志请用 ASCII 输出（JSON 序列化用 `ensure_ascii=True`），否则中文会话名会让日志变乱码，事后无法追溯删了什么。

## 6. 参数（照此实现）

- 空闲判定：10 分钟
- 重试间隔：30 分钟，最多 6 次
- 数据库备份：开启，保留最近 5 份
- 豁免规则：不豁免任何工作区，一律按 14 天清理

3. **开机触发脚本**：放入 Windows「启动」目录，登录后延时 2 小时静默运行。
4. **手动触发入口**：可双击的批处理文件，带 8 秒倒计时可取消，方便我在离开电脑前手动启动。

## 附录 A：Antigravity 已知数据布局（动手前必读）

以下来自公开资料，**仍需你在本机核实**。

### 候选路径

| 用途 | 路径 |
|---|---|
| 全局状态库（侧边栏索引所在地） | `%APPDATA%\Antigravity\User\globalStorage\state.vscdb` |
| 2.0 独立版可能的位置 | `%APPDATA%\Antigravity IDE\User\globalStorage\state.vscdb` |
| 对话正文件（`.pb`） | `%USERPROFILE%\.gemini\antigravity\conversations\` |
| 会话思考/任务追踪数据 | `%USERPROFILE%\.gemini\antigravity\brain\` |
| 其他大目录 | `backups/`、`browser_recordings/` |
| 工作区级状态 | `%APPDATA%\Antigravity\User\workspaceStorage\<id>\` |
| 缓存 | `Cache/`、`GPUCache/`、`CachedData/`、`History/`、`Local Storage/`、`Session Storage/` |

### 关键陷阱：索引不是普通表

`state.vscdb` 是 VS Code 风格的单表键值库（`ItemTable`）。对话索引存放在键
`antigravityUnifiedStateSync.trajectorySummaries` 中，值是 **base64 编码的 protobuf 数组**，
每个条目含会话 UUID、标题、创建/修改时间戳、工作区等字段。

这意味着：**你无法用 SQL 按时间条件删掉某几行**，必须先解码、过滤、再重新编码写回。
手写 protobuf 编解码极易出错，一旦写坏整个侧边栏历史就全没了。

### 推荐方案：删索引键，让程序自己重建

1. 备份 `state.vscdb`。
2. 删除超过 14 天的 `.pb` 正文件（及其对应的 `brain` 数据）。
3. 整条删除索引键：
   `DELETE FROM ItemTable WHERE key='antigravityUnifiedStateSync.trajectorySummaries';`
4. 下次启动 Antigravity 时，它会自动扫描剩余本地文件并重建侧边栏索引。

这个方案的好处是**结构上不可能出现索引与磁盘不一致**——索引是从事后剩下的文件重建出来的。
而且失败时最坏结果是"什么都没删"（把备份的 `state.vscdb` 拷回去即可完整还原）。

**注意**：重建依赖 `.pb` 文件本身携带的元数据。请先在**一份副本**上小范围验证：
删掉索引键、重启、确认侧边栏能正确重建且时间戳正常。**验证通过后再对真实数据动手。**
如果重建结果异常（条目丢失、时间戳归零），立即还原备份并告诉我。
